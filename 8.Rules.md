# SkillBridge — Team Rules & Conventions

## 1. The non-negotiable rule: data honesty
This applies to code, seed data, the pitch deck, and live Q&A with judges equally.
- **Never claim a data source you haven't actually implemented.** If AYUSH skill data is manually curated by the team, label it that way — "flagship domain sample data" or "illustrative dataset," not "sourced from AIIA's official curriculum" unless that integration genuinely exists.
- The platform is described as **domain-agnostic infrastructure** with **AYUSH as the flagship implementation** — not "an AYUSH-only platform," and not "built on official ministry data" unless true.
- Every score shown anywhere (UI, deck, demo) must trace to a real, inspectable formula. No hardcoded "for the demo" numbers presented as computed.
- If asked in Q&A "is this real AIIA/NCISM data?" — the honest answer is prepared in advance and matches what's actually in the seed script.

## 2. Git & branching
- `main` — always demoable.
- Feature branches: `feature/<module>-<short-desc>` (e.g. `feature/assessment-mcq-scoring`).
- Commit messages: imperative mood, one line summary + optional body — `Add MCQ scoring to Assessment Engine`.
- No direct commits to `main` during the build window once Phase 1 is stable — small team can relax this if it's genuinely slowing things down, use judgment.

## 3. API conventions
- Follow techspec.md §4 exactly: `/api/v1/`, `{ success, data, error }` envelope, `breakdown` object mandatory on every score-producing response.
- Validate all input server-side, even if the frontend already validates (see security.md).
- New endpoints get a one-line comment stating what role(s) can access them.

## 4. Design & content rules (from the design brief)
- Skill status colors are fixed meaning, not decoration: pine = verified, ochre = in progress, rust = gap. Never reuse these hues for anything else in the UI.
- One orchestrated motion moment on the homepage; everywhere else, motion responds to user action only (open/expand/confirm) — no default hover/scroll animation sprinkled on every card.
- Copy is written from the end user's perspective, active voice, plain language: name things by what the user understands ("My Skills," not "Competency Vector"). A button that says "Apply" produces a confirmation that says "Applied" — never rename an action mid-flow.
- No generic AI-design tells: no ALL-CAPS eyebrow labels, no middle-dot meta strings, no arrow-suffixed buttons, no uniform-shadow card grids. See design.md §5 for the full list.

## 5. Definition of done (per task)
A task is `DONE` only when:
1. It works against real seed data, not mocked/stubbed responses.
2. It matches the schema in schema.md (or the schema was updated first, deliberately).
3. It's been clicked through once by someone other than the author.
4. It doesn't break the end-to-end demo script.

## 6. Assessment integrity (product rule, not just security)
- Randomize question order per attempt.
- Don't let the frontend hold correct answers in client-side state/response payloads before submission.
- A skill can only move to `verified` through an actual scored assessment attempt — never by admin toggle in the demo build (if you need a demo shortcut, log it clearly as a dev-only seed action, not a real verification path).

## 7. Review checklist before any merge to `main`
- [ ] No secrets committed
- [ ] No hardcoded demo numbers presented as computed
- [ ] Matches API envelope + `breakdown` convention
- [ ] RBAC checked — right roles can/can't access the endpoint
- [ ] Doesn't regress the core end-to-end demo
