# SkillBridge — Technical Specification

## 1. Stack
- **Frontend:** Next.js (React) + TypeScript + Tailwind CSS
- **3D/animation (homepage only):** React Three Fiber (Three.js) with a static-image fallback for `prefers-reduced-motion`
- **Backend:** Node.js + Express, TypeScript
- **Database:** MongoDB (Atlas for hackathon), Mongoose ODM
- **Auth:** JWT access tokens + role-based access control (RBAC) middleware
- **Hosting (hackathon):** Vercel (frontend) + Render/Railway (backend) + MongoDB Atlas free tier

## 2. High-level architecture
```
Client (Next.js)
 └─ role-aware app: Student / Industry / Institution / Academician / Ministry
        │  REST/JSON over HTTPS
        ▼
API Layer (Node/Express) — /api/v1
 ├─ Auth & RBAC middleware
 ├─ Domain & Skill Management module   (domain-as-config)
 ├─ Assessment Engine
 ├─ Skill Gap Engine
 ├─ Matching Engine
 ├─ Learning & Training module
 ├─ Opportunity / Application module
 ├─ Collaboration module (academician ↔ industry)
 └─ Analytics / Aggregation module
        │  Mongoose
        ▼
MongoDB  (collections defined in schema.md)
```

## 3. Module responsibilities
- **Auth & RBAC** — signup/login, JWT issue/verify, role guard middleware (`student | industry | institution | academician | ministry | admin`).
- **Domain & Skill Management** — CRUD for `Domain`, `SkillCategory`, `Skill`. Domain-as-config: adding a new field (e.g. Engineering) is a data operation, not a code change.
- **Assessment Engine** — serves question sets by skill + domain; MVP supports `mcq`; schema supports `rubric`/`video` types for later. Scores attempts, writes `SkillResult`.
- **Skill Gap Engine** — compares a student's `SkillResult`s against an opportunity's required skills/thresholds; outputs per-skill and overall gap.
- **Matching Engine** — deterministic, weighted, documented formula producing a Readiness/Match Score plus a structured explanation (see schema.md `MatchResult`). No opaque AI scoring.
- **Learning & Training** — maps a specific gap to a recommended resource (curated external links in MVP).
- **Opportunity / Application** — CRUD for opportunities; application state machine (see appflow.md).
- **Collaboration** — CRUD for academician-facing listings: FDP, guest lecture, mentorship, research, live project.
- **Analytics / Aggregation** — institution- and ministry-level rollups via precomputed aggregation pipelines, not live per-request computation.

## 4. API conventions
- REST, JSON, versioned: `/api/v1/...`
- Resource-based routes, e.g. `GET /api/v1/students/:id/skills`, `POST /api/v1/opportunities/:id/match`
- Standard response envelope: `{ success: boolean, data, error }`
- List endpoints: `?page=&limit=&domainId=`
- Every scoring endpoint response includes a `breakdown` object — never a bare number.

## 5. Non-functional requirements
- **Explainability** — mandatory `breakdown` on all score responses (see techspec §4).
- **Performance** — dashboard aggregates are precomputed on write/cron, not computed live.
- **Accessibility** — WCAG AA contrast minimum, full keyboard navigation, `prefers-reduced-motion` respected on the homepage animation.
- **Scalability (post-MVP)** — new domains added via data (Domain/SkillCategory/Skill documents), no code changes.
- **Security** — see 9.security.md.

## 6. Environments
- `dev`, optional `staging`, `demo/prod`.
- Secrets via `.env`, never committed (Mongo URI, JWT secret, third-party keys).
