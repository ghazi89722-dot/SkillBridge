# SkillBridge — Security Considerations

## 1. Authentication & authorization
- Passwords hashed with bcrypt (never store plaintext, never log passwords).
- JWT access tokens, short expiry (e.g. 1h) + refresh token flow for longer sessions.
- RBAC enforced server-side on every route (never rely on the frontend hiding a button as the only access control).
- Ministry role is **read-only** and admin-provisioned — no self-signup path, to prevent impersonation of a government stakeholder.
- Industry and Institution accounts require admin/manual verification before they can post opportunities or view student data (`verifiedByAdmin` flag) — prevents fake-recruiter data harvesting.

## 2. Data protection & privacy
- Treat student profile data, assessment history, and AYUSH clinical-training records as **sensitive personal data** — apply India's Digital Personal Data Protection (DPDP) Act, 2023 principles: purpose limitation, minimal collection, and a clear basis for processing.
- Students should be able to request deletion of their account/data (right to erasure) — design the schema so this is a real, executable operation, not just a policy line.
- No sharing of individual student data with Institution/Ministry dashboards — those views must only ever show **aggregated, anonymized** analytics (see `InstitutionAnalyticsSnapshot` / `MinistryAnalyticsSnapshot` in schema.md — they store aggregates only, never individual identifiers).
- Industry sees individual student data only for students who have actually applied/matched to their specific opportunity — not the full student database.

## 3. Input validation & injection protection
- Validate and sanitize all input server-side (schema-based validation, e.g. Zod/Joi) — for every field, including nested arrays like `requiredSkills`.
- Use Mongoose schema validation as a second layer, not the only layer.
- Escape/sanitize any user-generated text rendered back in the UI (opportunity descriptions, feedback comments) to prevent stored XSS.

## 4. Assessment integrity (preventing gamed scores)
- Randomize question order and, where possible, question pool per attempt.
- Correct answers never sent to the client before submission; scoring happens server-side only.
- Rate-limit assessment attempt submissions per skill (e.g. cooldown before reassessment) to prevent brute-force score inflation.
- Log every status transition (`claimed → assessed → verified`) with a timestamp and the triggering `AssessmentAttempt` id, so a verified skill is always traceable to a real scored event — this audit trail is also what makes the "Verified" claim defensible to judges and to real recruiters.

## 5. API & infrastructure hardening
- Rate limiting on all public endpoints (especially auth and assessment submission).
- CORS restricted to known frontend origin(s).
- HTTPS enforced everywhere (Vercel/Render provide this by default — don't disable it).
- Centralized error handling that never leaks stack traces or internal identifiers to the client in production.
- Secrets (Mongo URI, JWT secret, any third-party API keys) in environment variables only, never committed — see Rules.md §7 review checklist.

## 6. Audit logging
- Log (with timestamp + actor id): skill verification events, opportunity creation, application status changes, and any admin-level account verification actions.
- Ministry/Institution aggregate views should be reproducible from these logs if a judge/stakeholder asks "how was this number generated."

## 7. Threat model summary (MVP-relevant)
| Threat | Mitigation |
|---|---|
| Fake student/industry accounts polluting data | Admin verification for industry/institution; rate-limited signup |
| Credential stuffing / brute-force login | Rate limiting + account lockout after repeated failures |
| Tampering with verification status via API manipulation | Server-side-only status transitions, tied to a real `AssessmentAttempt` |
| Scraping the full candidate database | Industry access scoped to applicants on their own opportunities only |
| Assessment answer leakage inflating scores | Correct answers never sent client-side pre-submission |
| Over-claiming data provenance (trust/reputational risk) | See Rules.md §1 — data honesty rule |

## 8. Post-MVP security roadmap
- Move to a proper credential wallet (DigiLocker/NAD-linked) for skill passport portability and stronger identity verification.
- Consider tamper-evident anchoring (e.g. hash-anchoring skill verification events) if the blockchain-credential direction from schema.md is pursued.
- Formal penetration test before any real production deployment beyond the hackathon demo.
